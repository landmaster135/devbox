コミットログを分析し、開発傾向と改善点をターミナルにレポート出力するスキル。

## 引数

- 期間: デフォルト1カ月。ユーザーが「3カ月」「半年」「100コミット」等で指定可能
- パス: 省略時はカレントディレクトリ。サブプロジェクト名や相対パスで指定可能

## 手順

### 1. データ収集（1回のBashで完結させる）

対象ディレクトリに`cd`してから実行。追加のgitコマンドは原則不要。

```bash
cd <対象パス> && \
echo "=== LOG ===" && git log --since="1 month ago" --format="%H|%ai|%s" && \
echo "=== COUNT ===" && git rev-list --count --since="1 month ago" HEAD && \
echo "=== STAT ===" && git log --since="1 month ago" --stat --format="COMMIT:%s" && \
echo "=== FILES ===" && git log --since="1 month ago" --format="" --name-only | sort | uniq -c | sort -rn | head -20 && \
echo "=== BRANCH ===" && git branch -a --format="%(refname:short)" && \
echo "=== AUTHORS ===" && git shortlog -sn --since="1 month ago"
```

### 2. レポート生成

収集データから以下のレポートを組み立てて出力する。追加のgitコマンド実行は避ける。

**フォーマットルール**:
- セクション見出しは `### 見出し名` 形式で統一する。`■`、`---区切り`、`【】`は使わない
- データを表示するすべての項目でバー表示（`████░░░░`形式）を使用する
- バーとデータ以外の装飾記号（`(*)`, `←`, `★`等）は一切付けない
- 「最多」はソート順が自明でない文脈（曜日別、時間帯別など順序固定の一覧）でのみ使用。降順ソート済みリストの先頭には付けない。同値は「最多タイ」

```
========================================
  Commit Insights レポート
  対象: <リポジトリ名>
  期間: <開始日> 〜 <終了日>
  総コミット数: <N>
========================================

## 1. コミット頻度・パターン
- 日別コミット数分布（バー表示）
- 週別コミット数（バー表示）+ 週ごとの変更種類比率の推移
  （時系列トレンドをここに統合。feat→fix移行等のフェーズ変化を読み取る）
- 曜日別の傾向（バー表示）
- 時間帯別の傾向（バー表示）
- コミット間隔（平均・最大ブランク）

## 2. 変更種類の分布
- Conventional Commits種別の内訳（バー表示、降順ソート）
- 種別が読み取れないコミットはメッセージ内容から推測して分類
- 偏りがある場合その指摘

## 3. ファイル変更ホットスポット
- 変更頻度Top10（バー表示、降順ソート）
- ディレクトリ別の変更集中度（バー表示、降順ソート）
- 1コミットあたり変更ファイル数の分布（バー表示）
- 巨大コミット（10ファイル以上）の一覧
- 各データに対して、なぜそうなっているかの分析コメントを付ける
  （例: 「config.pyが14回で突出。releaseコミットごとのバージョン番号更新が原因」等）

## 4. 総変更量
- 変更ファイル数（延べ）、挿入行、削除行、純増
- 1コミットあたりの平均値（平均変更ファイル数、平均挿入行、平均削除行）

## 5. 開発フロー観察
- ブランチ利用状況、コミット粒度、メッセージ品質を簡潔に記述

## 6. 改善提案
3〜5個。以下の観点を含めて検討する:
- 業界ベストプラクティス（GitHub Flow、Trunk-Based Dev等）との比較
- ツール・自動化（commitlint、release-please、pre-commitフック等）
- ホットスポットから見えるアーキテクチャ課題（責務集中、分割余地等）
- データに基づく根拠と、具体的な改善効果を示す
```

## レポートのトーン

- 事実とデータに基づいた客観的な記述に徹する
- 主観的な評価（「素晴らしい」「問題がある」等）や励まし・お世辞は不要
- 建設的なフィードバックを心がける。改善提案は、根拠があるものを優先して提出する。また、無理に理由付けしない
- 良い傾向も悪い傾向も同じトーンで淡々と報告する
